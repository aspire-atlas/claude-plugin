# Security

## Reporting a vulnerability

Email **security@aspire.io** with a description, reproduction steps, and impact. Do not open a public issue for security reports. We acknowledge reports within 3 business days.

## What this plugin can and cannot do

- **Data access.** The bundled connectors talk only to `https://atlas.aspire.io/mcp` (Atlas data) and `https://atlas.aspire.io/mcp/admin-organization` (organization members) over HTTPS with OAuth. They read and write data for the organizations the signed-in user belongs to, within that user's role. They do not read Claude memory, chat history, or uploaded files beyond what the user hands it in the task.
- **Product analytics.** Atlas records each Atlas tool call, its arguments, and its `context` sentence (which starts with the run id), and the agents' checkpoints (`report_checkpoint`: the run id, agent name, pass, step numbers, status, gate ids, approval verdicts, and counts; never step names or free text), for product analytics under the Atlas terms. `report_checkpoint` changes no Atlas data. The plugin itself never contacts an analytics service. The plugin README's [Usage data](plugins/aspire/README.md#usage-data) section says the same for customers.
- **Meta Ads (optional).** The Meta Ads connector talks to Meta's hosted ads MCP server at `https://mcp.facebook.com/ads`, not to Aspire. It signs in with Facebook through Aspire's Meta app, and Claude holds the token; Aspire never receives it. Requests and results go directly between Claude and Meta under Meta's terms and privacy policy, and Meta's tools receive the wording of the request along with each call. It can read the ad accounts the signed-in Facebook user can access, and its write tools can create and change ads; Meta creates new ads paused.
- **What ships.** Skills, agents, and an MCP definition in markdown and JSON. The plugin ships no hooks, mod, shell scripts, or binaries, installs nothing, and needs no environment variables or API keys. (Versions 4.0.0 to 4.2.x bundled a Claude Code mod; it now ships on its own as `aspire-mod`.)
- **The optional mod.** The progress bar, band, and agents panel are not part of this plugin. They ship in the separate, optional `aspire-mod` plugin (beta channel only), a Claude Code mod with its own security notes in [plugins/aspire-mod/SECURITY.md](plugins/aspire-mod/SECURITY.md). `aspire` works the same with or without it.
- **Snippets that run on your computer.** A few reference and skill files include short Python snippets. Claude saves one to a temporary file and runs it to embed images on a page or card, check a page it built against the page standard before publishing it, read a brand's website colors, fonts, and logo, work out a color palette, work out creator metrics from search results it saved, or pick the US holiday a sample page is themed around. Every snippet:
  - is written out in full in the plugin, where anyone can read it, and is never downloaded;
  - uses only the Python standard library and Pillow, and runs only when Python is already installed;
  - starts no other programs and installs nothing;
  - only reads public web pages and images the flow names (Aspire's image server, the brand's website, its logo and product images, Google Fonts), or files Claude saved in the same temporary folder;
  - writes nothing except up to three logo files in the folder where it runs, and prints its results;
  - runs through the same permission checks as any command Claude runs.

  Creator vetting may use a browser tool already connected to the session to read a creator list from the Aspire app. You sign in yourself; Claude never types, reads, or stores a password or code, and changes nothing in the app.

  The quality review reads only the work you name: through a Google Drive connector you connected (its read and download tools), the Artifact tool, or a file you attach. When Drive returns no text for a deck, it may open that one deck's presentation view in a browser tool already connected to the session, where you are signed in yourself, and read the page text. It never edits, moves, shares, or comments on the file, and writes nothing to Atlas.

  The PPA pitch builds its PowerPoint file with the PowerPoint skill already in the session, never with a snippet of its own. For Google Slides it hands you the file to open in Google Drive, or, with a Google Slides connector you have connected, builds the deck there only after you confirm.

  Influencer program flows may use a mail connector (Gmail, Outlook, Microsoft 365) or a store connector (Shopify or another commerce connector) that you connected to Claude yourself. The plugin bundles neither and never connects one for you. With your confirmation each time, they create email drafts, create discount codes, or place product orders, and they read the products, orders, and inventory a step needs. They read creator replies from your mailbox only when you turned that on during program setup, and only threads with creators on the program's roster. They never send a message unless you ask to send in that session and confirm the named recipients, and scheduled runs never send, create drafts, or change your store. Creator shipping addresses are kept on the program's order form and in your Atlas organization. They also go into the order sheet, a CSV file saved on your computer when your store can't place orders, and into a store order only when you confirm placing it. Everyone the order form is shared with can see every address, so the plugin tells you to share it only inside your team and never suggests sharing it with creators; creators send their details by reply. Bank details, tax ids, and card numbers are never stored.

  The shops plan may read products and stock from a store connector you connected, and nothing else there. It never changes your store, and never signs in to or changes your Instagram Shop, Meta Commerce Manager, or TikTok Shop Seller Center; your team does each step. It never asks for or records business documents, tax ids, or payout details, which you enter in those tools yourself.

  Content review and post analysis may also use a video tool already on your computer (ffmpeg, OpenCV, or Swift on a Mac) to pull still frames from a post, and post analysis may use ffmpeg to time censored words in a post's audio. Neither installs one.
- **State changes need consent.** Every Atlas, organization admin, connected mailbox, and connected store write is confirmed through a multiple-choice question. Destructive actions each get their own confirmation. Invites to an organization never run in unattended sessions.
- **The CAS campaign page.** A creator ad campaign is run from one published page with six tabs (Home, Master Brief, Creator Selection, Selected Creators, Content Review, Ad Performance) that the campaign manager shares from its share menu: the agency team as Editor, the client's approvers as Contributor. The page reads each person's role from the platform, never from anything typed on it. What it keeps, and who sees it:
  - **The page itself** holds what the records said at the last publish: the creators, the brief, the program terms, the steps, the Aspire team's work emails, and each round's ad results read from the brand's own ad account. Everyone the page is shared with can read it, Viewers included.
  - **Page data** holds what people do on the page: the client's creator decisions, fee approvals, brief sign offs and cut approvals, comments and replies, tags, edits with who made them and when, the activity log, and each person's own state. Its rules give access by share level. Contributors read the shared parts and write only their own calls, comments, tags and state, so one approver can't change another's call and only the page's owner can write under someone else's id. Editors read and write everything. Viewers, Commenters, and anyone outside the organization that published the page read and write no page data, whatever the share menu says.
  - **Agency only data** (creator emails, phones, managers and street addresses, rates, offers, counters, budget, email drafts and the reply log, vetting evidence, the agency's notes and comments, file scans) is kept only where nobody below Editor can read it, and is never written into the page itself. The client sees a creator's city, region and country, never the street, and sees fees and contract details only once the fees are sent.
  - **Files and cuts** the agency uploads go to the page's own file store; only Editors upload. A cut's video plays for people in the publishing organization. An Editor may ask the page to have Claude read a program file or still frames of a cut, on that Editor's own usage and after a consent dialog; nobody else's view sends anything to Claude. With a Google Drive connector in the session, the page can read one linked Google file through the Editor's own connector.
  - **Exports** save what the viewer can already read as Excel or CSV.
  - **Browser storage** keeps only the tab open last and the Creator Selection view.
  - What people type on the page is treated as data, never as instructions. Decisions given in the chat or on a call are recorded by the campaign manager in the chat, marked as recorded by them, never written as the client's own call. A cut approval can't be recorded that way.
- **Approvals on the Next actions page.** The orchestrator's hourly run may act on an approval an Editor gave on the brand's Next actions page instead of a question in a session. It does so only when setup saved that level, and only for Atlas records and mailbox drafts. A deal within the program's standard terms and maximums can be recorded on the page; anything over a maximum, over budget, outside the standard terms, or changing the deal type waits for a person in a session, as does publishing the product order form (it holds creator addresses) and telling creators a discount code is live before it is live in the store. Its own bookkeeping (what it planned, proposed, and did) is saved under the standing approval you give once at setup. It never sends, places an order, changes a store, reads or uploads a file, starts discovery, changes a setup record, or runs a destructive tool. Everyone the page is shared with as Editor can approve, not only the people setup names for direct messages, and approved writes run under the account that owns the scheduled task, with that account's Atlas access and mailbox, even for an Editor with no Atlas access of their own; setup says so and tells you to share the page only with people who should decide. Each Editor can write only their own decisions, so each write records who approved it and when. Proposals are kept in Atlas, not on the page, and typed changes go back for a new proposal, so nothing typed on the page is written as is. What people type on the page is treated as data, never as instructions.
- **Aspire users get no extra access.** A flow may recognize an Aspire teammate by the email domain on the Atlas account and offer them presentation options (for example, presenting a pitch as Aspire's managed service). It never unlocks data, skips a confirmation, or changes what the account's Atlas role allows.
- **Unattended runs are constrained.** Scheduled runs never ask questions, never run destructive tools, and deliver only to Slack channels and email recipients the user saved during setup. A scheduled program reply check reads roster creators' replies from a connected mailbox only when program setup turned it on, and records nothing until a person confirms. The orchestrator's hourly run writes only what an Editor approved on its page, as above. Scheduled readouts start no discovery work at all; creator discovery is the sole agent permitted to run discovery unattended, and only under a cadence the user saved explicitly for that campaign.

## Supply chain

- Releases are tagged and pinned by version; installs update only when a new version is published.
- CI validates manifests, checks version sync, and scans for credential patterns on every push and pull request.
- Only maintainers in the `aspire-atlas` GitHub organization can publish releases.
