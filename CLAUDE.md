# Working in this repository

This repo is the marketplace catalog for Aspire Atlas's customer plugins for Claude, one plugin per folder under `plugins/` (today `aspire`). Full operating rules: `docs/PLUGIN-LIFECYCLE.md`. The short version:

- `develop` is the beta channel (marketplace `aspire-atlas-beta`, version = commit SHA). `main` is the official channel (marketplace `aspire-atlas`, each plugin's version pinned on its own entry in `.claude-plugin/marketplace.json`).
- Feature work: branch from `develop`, PR into `develop`. Never edit a changelog (`CHANGELOG.md` for `aspire`, `plugins/<name>/CHANGELOG.md` for the others) or the channel-specific lines of `.claude-plugin/marketplace.json` (top-level `name` and `description`, each plugin's `displayName`, `version`) on `develop`. Plugin entries' `description`s are shared and stay identical on both branches.
- Releases: `git checkout -b release/X.Y.Z origin/main && git merge origin/develop`, bump the version of each plugin whose folder changed (for `aspire`, the top-level `version` too), write each one's changelog entry, and remove the entry of any plugin not ready for `main` to hold it back, PR into `main` with a merge commit. CI tags (`vX.Y.Z` for `aspire`, `<name>--vX.Y.Z` for the others) and publishes.
- No `plugins/<name>/.claude-plugin/plugin.json` or `SKILL.md` frontmatter carries a `version`.
- Plugins live in `plugins/<name>/` with `"source": "./plugins/<name>"`; `scripts/plugins.sh` holds the per-plugin conventions the checks and workflows share. A new plugin follows section 14 of `docs/PLUGIN-LIFECYCLE.md`, links the files it shares with `aspire` (the artifact standard, the marks) instead of copying them, and ships no hooks, mod, or script files unless a deliberate decision adds them.
- Never touch `aspire-atlas/claude-plugin-internal`; CI overwrites it from `develop`.
- Plugin content is markdown and JSON, plus one Claude Code mod added by deliberate decision in 4.0.0: the TypeScript function-hooks module in `plugins/aspire/hooks/` (with its tests) and its state contract `plugins/aspire/types/index.d.ts`. The mod must stay as `SECURITY.md` describes it: inert until `/aspire` runs, an Atlas tool result passes, or an `aspire:*` agent starts, reads only what already passes through the session, registers only its display-only `aspire_progress` tool, changes no other tool call, result, prompt, or agent, and makes no network, file, or process calls (review the hooks and calls `claude plugin validate plugins/aspire` lists, and run `claude plugin test plugins/aspire`). Python snippets inside markdown are allowed when they follow the snippet rules in `SECURITY.md`. Widening what the mod does, any other hook, script file, or binary, or a snippet that breaks those rules needs a deliberate decision and a major version.
- **Brand every Aspire surface the same way.** The Aspire Atlas look is one animated mark (`plugins/aspire/assets/`, generated from `hooks/logo.ts`), its dark tile and teal, and the lime `#C8E36B` accent (the atlas.aspire.io call-to-action color) for motion and emphasis. Every page, card, and widget carries the mark and the source line per `skills/aspire/references/artifact-standard.md`; a running state uses a spinner from the assets (the twin-comet one in the Atlas tool row), whose colors a page can set with `--spinner-bg`, `--spinner-color`, `--spinner-glyph` (and the `-light` forms) or its `--brand`. The mod brands only the render sites `SECURITY.md` lists: the tool-call row and group, the question dialog, the spinner, the closing turn line, the hint under an idle prompt, the plugin's own command output, the band, the panel, and the Artifact card. Each is display only, runs only while the mod is on (the question dialog and spinner only while the skill reports progress), keeps Claude Code's own drawing and adds to it, holds the engine drawing exactly once at the question dialog, and gives the terminal, which draws no Svg, the cell mark. The mod never restyles the model's or the person's messages, session notices, mode labels, or anything before `/aspire` has run. Branding another site, or widening one, needs the site added to this list and to `SECURITY.md` in the same change, a test, and a major version.
- `/aspire getting started` and `/aspire help` show the Atlas Starter Guide (`references/first-run.md`) and never start onboarding; keep that route and the guide's copy true when a flow changes.
- Every Atlas write in a skill or agent is confirmed with `AskUserQuestion` first, except that the orchestrator's hourly run may act on an Editor's approval on the Next actions page for Atlas records and mailbox drafts only (`references/orchestrator.md` **4**; widening it needs a major version), and writes its own bookkeeping findings on the `orchestrator-` prefix under the standing approval its setup (X6) gave, as a cadence record does; destructive tools each get their own confirmation; unattended runs never ask and never destroy; only `atlas-creator-discovery` may start discovery work unattended, under a cadence the user saved for that campaign.
- Before pushing: `claude plugin validate .`, `claude plugin validate plugins/<name>` for each plugin, `bash scripts/check-channel.sh <develop|main>`, `bash scripts/check-tool-contract.sh`, `bash scripts/check-agent-roster.sh`, `bash scripts/check-artifact-standard.sh`, `bash scripts/check-palette.sh`, `bash scripts/check-skill-args.sh`, `bash scripts/check-directory.sh` (Claude Code swaps `$0`, `$1`, … and `$ARGUMENTS` in a skill or command body for the command's arguments, so write an amount there as `USD 2,000`, never `$2,000` or the `\$` escape, which agents reading the file see). A new agent goes in its plugin's skill hand-off table, the plugin README table, and, in a plugin with the agents panel, `hooks/roster.ts` and `hooks/costumes.ts`; the roster check fails until it does. Every agent and every page it publishes follows `skills/aspire/references/artifact-standard.md` (the animated mark and the footnote); a new agent copies the "Artifact standard" block verbatim from section 5 of that file, and the wording of the mark and source line is changed only there, or the last check fails. What a page says and its E1 to E12 self-check live in the shared `skills/page-standard/SKILL.md` (never a command); its script is tested against `scripts/fixtures/page-standard/` by the same check.
- **Answer the plugin directory by its rules and ours.** A blocking finding from the directory's scan is fixed in the plugin; a warning or note is fixed only when it does not break a rule here, and the findings kept on purpose are listed with their reasons in section 10 of `docs/PLUGIN-LIFECYCLE.md` (never add a `version` to `plugin.json` to clear its warning). `scripts/check-directory.sh` catches what the scan blocks before a push: in a mod, every helper that takes `$` is a function declaration and `$` is only ever a plain `$.noun.method(...)` call or a whole argument, with no brackets in a callback passed alongside it (`update($, atom, s => ...)`); no text file is over 256 KiB (split a long reference by section); and the plugin README's **What each hook does** names each tool the mod registers or answers and each prompt, message, and agent event it hooks.
- `contract/atlas-mcp-tools.json` is the Atlas tool surface the plugin is checked against. When the server's tools change, refresh it from the server repo's `tools-list.golden.json` with `bash scripts/check-tool-contract.sh --update <path>`, fix what the check then flags, and commit both together.
- No secrets, customer names, or internal URLs in any file.
- The Aspire Atlas Organization Admin connector and the `/aspire:org-admin` skill are support tools, not features. Never merchandise or promote them. Keep them out of the plugin and marketplace descriptions, keywords, README feature lists and summaries, changelog highlights, and any flow that suggests them unprompted. Mention them only where people need the facts: setup and connection steps, the component list, and security and data-access notes. The skill runs only when someone asks about members or invitations.
- **No internal tools.** This plugin is public and ships to customers, so everything in it is for customers. Never add a skill, agent, reference, or flow meant for Aspire employees (anything gated on a staff check, the Aspire organization, or an employee role, or described as "staff only" or "internal"). Never add or depend on an internal connector or system: an Aspire data warehouse or BI tool (Superset, Metabase, ClickHouse, and the like), Aspire's own Slack workspace, CRM, or support tools. The bundled connectors in `plugins/aspire/.mcp.json` are the only Aspire connectors the plugin uses; adding one needs a deliberate decision. Internal tools belong in a separate private repo.
- **Managed services are not internal tools.** Aspire teammates sometimes run a brand's own Atlas organization on its behalf. A customer flow may offer managed-service presentation options (Aspire branding, Aspire service packages typed in at run time, an Aspire-to-brand voice) when `/aspire` recognizes an Aspire user by email domain (**Aspire users** in the skill). The flow must still serve the brand, run only on the bundled connectors inside the brand's organization, work fully for brand users, and never gate data, tools, permissions, or confirmations on the flag. Never write Aspire prices or rate cards into a plugin file.
- **Check every change for internal tools.** Before committing, and when reviewing or merging a PR (including merging `develop` into a branch), search the diff for staff-only or internal content: `git diff origin/develop... | grep '^+' | grep -niE 'staff|internal|employee|warehouse|superset|metabase|clickhouse|aspire organization|slug .aspire.'`. Also check for any new server in a `.mcp.json`, any new directory under `plugins/`, and any new directory under a plugin's `skills/`. If you find something, stop and flag it to the user rather than committing or merging it. References to the release mirror in `docs/PLUGIN-LIFECYCLE.md` and `CONTRIBUTING.md` are fine.
